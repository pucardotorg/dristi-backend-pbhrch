# Parallel Migration Plan — 3 Devs, 27 Pending Services

Operating manual for the parallel migration push. Devs run
`/migrate-service` in their own Claude sessions; this doc is what
makes the parallelism work without conflicts or improvisation.

**Audience.** Migrating devs + their Claude sessions. Devs review the
lane assignments + queue + escalation rules. Claude sessions read this
on session start (auto-loaded via `scripts/migration/CLAUDE.md`).

---

- [ ] `monolith/main` has the API-first cutover (commit `7790b59c2` and follow-ups)

- [ ] **Smoke test:** one volunteer runs `/migrate-service template-configuration case-lifecycle templateconfiguration` end-to-end, lands the PR. Confirms the new flow before all 3 fan out.

## 1. The model — one active service per dev

| Slot | Contents | Dev attention |
|---|---|---|
| **Active** | Currently migrating service X | Full focus |
| **In-review** | Previous service, PR open, awaiting merge | Zero — coordinator handles |

Per-dev loop:

1. Claim next service from queue (§3).
2. `git checkout monolith/main && git pull && git checkout -b monolith/<service>`.
3. Run `/migrate-service <service> <module> <subdomain>`.
4. Push, open PR. Service moves to In-review slot.
5. Immediately claim next. Repeat.
6. When coordinator pings *"main moved, your branch needs rebase"* → run §5 manual merge recipe, re-verify, push.

No dev ever has more than one **active** branch.

## 2. Lane assignments

| Lane | Dev | Module ownership |
|---|---|---|
| **L1** | TBD | `case-lifecycle` independents (Tier 0/1) |
| **L2** | TBD | `case-lifecycle` dependents (Tier 2 after Tier 1 merges) + integration warmup |
| **L3** | TBD | `integration` + `identity-access` + `payments` |

**Why partition by module.** Each module has its own
`domain-<module>/pom.xml` and per-subdomain YAMLs. Devs in different
lanes never edit the same pom file — eliminates the most common rebase
conflict surface.

**Shared touchpoints** (still need merge-coordinator handling):
- `dristi-app/src/main/resources/application.yml` — append-only profile + flyway lists, trivial 3-way merge
- `dristi-app/src/main/resources/application-shared.yml` — regenerated by Pipeline 5
- `dristi-monolith/dristi-common/pom.xml` — rare, only when lifting DTOs needing legacy deps

## 4. Per-service Claude session

`/migrate-service <service> <module> <subdomain>` walks the recipe.
Key things the session will surface:

- **Pre-flight rebase check** — branch must be up to date with `monolith/main`.
- **Flyway action** — looked up from [flyway-suffix-allocation.md](flyway-suffix-allocation.md).
- **`<Subdomain>Api` declaration** (Rule 31) — surfaced for dev review of method shape before scaffolding.
- **REST → direct, both directions** (Rule 32) — `done` callers calling INTO this service AND this service's outbound calls.
- **`ModuleStructureTest`** runs as part of build verification.
- **Tier 3/4 escalations** — Claude stops; dev decides.

## 5. Manual merge recipe

When the coordinator pings *"main moved":*

```bash
# 1. Tree must be clean
git status

# 2. Fetch + merge (NOT rebase — Rule 28 commit boundaries)
git fetch origin
git merge origin/monolith/main

# 3. Resolve standard conflicts (almost always trivial)
# - dristi-app/src/main/resources/application.yml:
#     spring.profiles.active list:    keep both new profiles
#     spring.flyway.locations list:   keep both new locations

# 4. Re-run config consolidation with cumulative service list
#    (read SERVICE_REGISTRY.md to find every `done` service)
python3 scripts/migration/config_consolidation/run_consolidation.py \
  --service <each done> --service <my-service>

# 5. Re-verify gates + ModuleStructureTest
mvn -pl domain-<module> -am test -Dsurefire.failIfNoSpecifiedTests=false
mvn -pl dristi-app  -am test -Dsurefire.failIfNoSpecifiedTests=false

# 6. If Gate 7 collides (someone landed a Flyway file with my _<n>),
#    consult flyway-suffix-allocation.md, bump suffix, re-run gate.

# 7. Push
git push origin monolith/<service>
```

If anything fails outside the table or RUNBOOK §7, **stop, ping coordinator, surface as Tier 4 in your Claude session.** Do not improvise.

The fully-automated `/reconcile` command is deferred — see §9.

## 6. Merge coordinator role

One dev rotates into coordinator slot. Per merge:

1. Pull each PR as it gets review approval.
2. Run config consolidation **once per merge** with cumulative `--service` list:
   ```bash
   python3 scripts/migration/config_consolidation/run_consolidation.py \
     --service <every done service including just-merged>
   ```
3. Update `dristi-app/.../application.yml` `spring.profiles.active` list (append the new subdomain).
4. Verify: `mvn -pl dristi-app -am test`.
5. Commit + push as `chore(monolith): consolidate after <service> merge`.
6. Ping the other 2 devs.

Slot ≈ 15-20 min per merge. Coordinator still ships their own services.

### Rotation

Rotated among the 3 devs as the team agrees. Whoever holds the slot
absorbs interruptions from the other two and runs config consolidation
+ the post-merge `chore(monolith)` commit.

## 7. Cross-`*Api` coordination (Rule 39)

When your Claude session surfaces *"Service B needs `<T>Api.method()` that doesn't exist":*

Two options (Rule 39):

1. **Coordinate cross-PR.** Reach out to whoever owns `T` — ask them to expose in their PR, or open a small `feat(<t>): expose <method>` PR yourself, scoped only to the addition.
2. **Leave as REST temporarily.** Document in your `_rest_calls.txt` audit trail.

Devs talk to each other directly — no coordinator routing. You have the domain context.

Do **not**: edit `<T>Api.java` from your branch, infer method shape, or drop the conversion silently.

## 8. Escalation rules — when to stop

Claude in your session stops on:

- Tier 3 design questions (Rule 18 widening, Rule 35 cross-module write, contract DTO promotion).
- Tier 4 facts only the dev knows (REST host = eGov vs DRISTI, intent of a `@Value` default, ambiguous Flyway year).
- `ModuleStructureTest` violation that can't be fixed by switching to a `*Api`.
- Cross-`*Api` method gap (Rule 39).
- Pipeline gate FAIL not covered by RUNBOOK §7 / PIPELINE_RULES.md.
- Build failure with non-obvious root cause.

When Claude stops: it surfaces the question + options. You decide. It executes.

Do not pressure Claude past a hard stop.

---

## 9. Deferred — `/reconcile` automation

The fully-automated rebase + reconcile pipeline is deferred until
rebase friction warrants it. After the first wave of merges, review:

- How many rebases? (count coordinator pings)
- What friction came up? (read each Claude session's chat for rebase-related Tier 4 escalations)
- Was §5 sufficient, or did devs invent their own fixes?

If 3+ rebases hit the same recurring friction, build the script. If rebases were clean, no script needed.
